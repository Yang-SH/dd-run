## 1. 第一轮结论复核（逐条重验）

| # | 结论 | 复核结果 |
|---|---|---|
| P1 | shell.rs `run_capture` 管道死锁→超时误杀 | ✅ **确认**（`crates/dd-ext/src/builtins/shell.rs:285-306`）。先 `try_wait` 后读管道；子进程输出超过 OS 管道缓冲（~4–64KB）即阻塞在写端、永不退出，3 秒被 kill 误报失败。**补充**：行 296 注释自称"进程退出后管道写端关闭，wait_with_output 不会死锁"——恰好答非所问：死锁发生在**等待退出之前**，注释与代码双双需要修正。search.rs `run_es` 已有正确写法（双管道 + 独立读线程），应统一 |
| P2 | calc.rs 大数 `as i128` 饱和显示错误 | ✅ **确认**（`crates/dd-ext/src/builtins/calc.rs:419-435`）。整数浮点走 `rounded as i128`，Rust 饱和转换，结果 ≥2¹²⁷（如 `2^128`）显示为 i128::MAX——计算器给出貌似正确的错误答案 |
| P3 | framing.rs 解码器 O(n²) | ✅ **确认**（`crates/dd-protocol/src/framing.rs` Decoder::push）。`position(b'\n')` 从头扫 + `drain(..=pos)` 全量搬移；半可信扩展 stdout 可借此拉高宿主 CPU |
| P4 | shell 危险命令确认门可绕过 | ✅ **确认**。`call del`、`d^el`（cmd `^` 转义）、`powershell -Command`、`wmic`、`robocopy /MIR` 均不命中 `is_dangerous_query`。项目定性为"防手滑护栏非边界"（诚实），但 UI 呈现有误导风险（见 §2 UI-6） |
| P5 | 信任台账 TOCTOU / 重钉窗口 | ✅ **确认**，且属已声明取舍（trust.rs 模块头明确"用户同意+变更检测，非防篡改"） |
| P6 | 平台层一致性（reveal 无门控 / file URL 不编码 / .bat+.cmd / MSRV） | ✅ **确认**。`manifest.rs:303` 确实按 `[".exe", ".cmd", ".bat"]` 解析；全 workspace **无 `rust-version` 声明**——BatBadBut（CVE-2024-24576）修复依赖 Rust ≥1.77.2，这条边界目前靠运气。**精确化**：清单由本地作者编写且经 S-05 信任门，非直接攻击面，属纵深防御/卫生问题 |
| P7 | 捕获钩子单槽 static 复用竞态 | ✅ 维持（低概率低危害） |
| P8 | 工程坏味道 | ✅ **确认**。`apps.rs` `steam_install_dirs` 硬编码 `G:\Program Files (x86)\Steam`（开发者盘符泄漏）；CI `--skip` 一个硬编码期望本机装 Flowframes 的测试；`Launch` 枚举注释残留 `cmd /c start` 旧描述 |

**复核修正**：无翻案项；P6.3 从"潜在注入面"精确化为"纵深防御卫生问题（信任门在前）"。

## 2. UI 设计与交互审查（新增）

### 2.1 做得好的（多数细节达到产品级）

1. **输入法（IME）兼容**（`ui/panel.rs`）：聚焦时每帧设置 `ime` 光标区域，中文组合输入的候选框定位正确——launcher 类项目的常见翻车点，这里处理了。
2. **悬停与键盘选择仲裁**：指针移动时才让悬停抢选择，键盘导航不被鼠标静止悬停干扰；双击/单击激活做成可配置项。
3. **加载骨架屏防闪烁**：短查询优先缓存兜底 + 延迟骨架显示，避免高频输入时 UI 抖动。
4. **捕获热键的异步钩子 + 自回声验证**（`platform/capture_hook.rs`）：UI 零阻塞，`F15` 自注入验证钩子真实生效（防安全软件剥离导致"假成功"），失败回落 egui 基础路径——Ctrl/Alt 组合永远可录。这是对 Windows 低级钩子不可靠性的罕见周到处理。
5. **设置页信息架构**：分类导航（外观/材质/密度/常规/备份/自定义命令/搜索行为/按键行为/搜索引擎/扩展）+ 卡片式分组 + 单选卡/滑杆/开关/下拉，材质主题带缩略图预览；文案中英双语走 i18n 键表。
6. **动效可关**：`animate_value_with_time` 过渡 + 全局动效开关（关闭时直出终态），空闲期零额外重绘。
7. **多屏/分辨率健壮性**：唤起时一次性定位光标屏（删除了启动期逐帧 recenter 轮询），V-14 真机腿覆盖分辨率变更后 screen_rect 重解析。
8. **页脚键帽提示**（手动绘制的 keycap）+ 超宽动作文本截断保单行，与设计稿逐行对齐。

### 2.2 问题与建议

| # | 问题 | 严重度 | 说明 |
|---|---|---|---|
| UI-1 | **缺 Home/End/PageUp/PageDown 导航** | 中 | `app/keys.rs` 全量按键集仅 ↑↓/Tab/Shift+Tab/Enter/Esc 等。"全部应用"数百项长列表只能逐行移动，对比 PowerToys CmdPal/Run 均支持 Home/End/PgUp/PgDn。长列表场景下这是最明显的便利性缺口 |
| UI-2 | **像素级手写布局的维护性** | 中 | `ui/panel.rs`/`row.rs`/`widgets.rs` 大量 `allocate_exact_size` + 手算 rect + 手绘 keycap。视觉一致性极好（逐行对齐设计稿并注释了设计稿行号），但字体度量/DPI 变化时脆弱，且新行类型成本高。属有意取舍（实现精确控制），建议至少为行高/间距建立单一常量表（部分已有 theme 常量） |
| UI-3 | **可访问性基本缺失** | 低（egui 平台限制） | 手绘 keycap/图标/自管焦点无屏幕阅读器语义、无高对比度模式。egui 生态普遍如此，但作为键盘优先的 launcher，至少应支持系统高对比度主题时提高色阶 |
| UI-4 | **emoji 全缺**（已声明取舍） | 低 | 移除 Segoe UI Emoji 后用户数据里的 emoji 呈豆腐块；有 `glyph_coverage_check` 工具兜底图标字形，属知情取舍，记录在案 |
| UI-5 | **设置页单文件 4104 行** | 低（组织性） | `ui/settings_view.rs` 按 card 函数组织尚清晰，但已是全仓最大文件，加卡片会继续膨胀。建议按 card 拆分模块 |
| UI-6 | **Shell 危险命令确认文案误导风险** | 中（与 P4 联动） | UI 呈现"危险命令需确认"易让用户高估防护，反而更敢粘贴不明命令。建议弹窗明示"本操作不拦截任何命令，请自行确认内容" |
| UI-7 | **每帧整列表克隆** | 低（性能，详见 §4） | `panel.rs` 渲染前 `filtered().map(clone).collect`，分组时再克隆一次。列表小无感，网格/长列表页可感知 |

## 3. 架构审查（新增细化）

### 3.1 分层与依赖（优秀）

```
dd-protocol（纯类型+成帧+信封，零宿主依赖，协议 v1.0 冻结）
   ↑
dd-host（清单扫描 / 子进程 JSON-RPC 客户端 / 信任台账 / 冻结缓存）
   ↑
dd-gui（egui 宿主：聚合、页面栈、平台层、in-process 适配）   dd-ext（共享扩展运行时）← dd-ext-sample
   ↑
dd-run-cli（自检/一致性 CLI，复用 host+ext）
```

- 依赖严格单向、无环；协议层只依赖 serde/log，`HOST_METHODS` 等字符串单一来源。
- **双通道等价设计**（M9 R1）：第三方扩展走子进程（隔离），内置 5 扩展 in-process 直驱 `serve_line`，两侧共用同一套 `classify` 路由——同一语义、两条实现路径有测试锚定等价性，这是本仓库架构上最漂亮的一处。
- 信任链三道门清晰：清单 §7 九条校验 → S-05 台账判定（Builtin/Sidecar/ThirdParty）→ spawn 前双哈希重验 + 受保护环境变量过滤（S-10）。

### 3.2 可商榷点

1. **巨型文件**：`settings_view.rs` 4104 行、`settings.rs` 2299 行、`keys.rs` 1300 行、`aggregator.rs` 1524 行。函数级组织尚可，但跨文件职责有重叠（settings 数据层 vs 设置视图层边界清晰，keys.rs 混合了导航/热键/捕获三职责）。仓库自备 `refactor-layering-plan.md`，说明作者有意识，建议落地。
2. **文档 sprawl**：35 篇文档 + 12 份 plan，虽有 `docscan` 工具与 doc-audit（2026-09-29）治理，plan 类文档随时间会与实现漂移（本轮抽查未见明显失配，但机制上依赖人工纪律）。
3. **错误处理风格**：全仓 428 处 `unwrap()/expect()`，绝大多数在测试与"不变量成立"处（如锁 poisoned 后 `into_inner()` 恢复、`Mutex::lock().unwrap_or_else` 模式），生产路径抽查未见会在用户输入路径 panic 的点；GUI 侧有 `crashlog.rs` + catch_unwind（in-process 扩展 panic 映射为 JSON-RPC -32603，宿主存活，有测试）。
4. **`answer_host_request` 异步语义**：宿主对已声明 `host/*` 方法立即回 `{}`、副作用由 UI 异步执行——协议文档应显式写明"响应到达 ≠ 副作用完成"，否则扩展作者会踩坑。

## 4. 运行速度审查（新增）

### 4.1 冷启动

- **CJK 字体异步化（L10）**：msyh ~19.7MB + seguisym ~2.5MB 改后台线程加载，就绪后 `set_fonts` 原子热替换——首帧不被 20+MB 字体解析阻塞，真机数据 data-ready < 200ms 达标（`implementation.md` 6.2，2026-09-05）。
- v0.2.0 冒烟台账冷启动 862ms（GUI 6 秒存活口径）——含进程拉起到可交互全链路，属正常范围；面板类工具对"热键唤起→可输入"路径已单独优化（隐藏窗口常驻 + 一次性定位），日常感知延迟不取决于冷启动。
- 构建侧 `lto="fat"` + `codegen-units=1` + strip：主程序 8.6MB、portable zip 4.3MB，体积控制好。

### 4.2 热路径（搜索/列表）

| 项 | 评价 |
|---|---|
| 模糊匹配 | nucleo + **Matcher 复用** + **分层打分**（标题层恒先于附属层，修真机"搜 steam 排第 5"）+ **拼音索引**（`jsq`→计算器）；内存优化计划中"nucleo Matcher 复用"经测量判定不做的决策有测量依据 |
| 聚合 | `thread::scope` 每扩展一线程并行拉取；冻结桩冷启动不 spawn（A6）；空闲到期逐出（A7） |
| 重绘策略 | egui 按需重绘：加载期 33ms 轮询、动画过渡期重绘、Toast 到期预约重绘、空闲零帧；`logic`/`ui` 分离（eframe 新 API），隐藏态轻量自愈检查 |
| 文本测量 | `text_width` 每次 `layout_no_wrap` + `String` 分配（`ui/widgets.rs:28`）；egui 内部 galley 缓存摊薄了主要成本，属可接受的小浪费 |

### 4.3 热路径问题

1. **每帧整列表克隆**（UI-7）：`page.list.filtered()` 后逐项 `clone` 两遍（扁平渲染一遍、分组渲染一遍）。200 项 × 每项数个 String × 30–60fps 下是可测量的分配压力。建议渲染借用或仅克隆可视窗口项。
2. **分组 O(n²)**：`groups.iter_mut().find` 线性查 section，n 为 section 数，影响小。
3. **framing O(n²)**（P3）：虽属协议层，落在"速度"维度同样成立——半可信扩展可拖慢宿主聚合线程。

### 4.4 文件搜索扩展（search.rs，独立 sidecar 进程）

- Everything 探测带 TTL 缓存（避免每次按键探测）；IPC 直连优先、`es.exe` 回落；可用性探测失败显式落成 `files.error` 引导项而非静默空列表。
- PATH_INDEX 容量有断言上限（512）防无界增长；图标 worker 独立线程，不阻塞主循环。
- 评价：sidecar 进程隔离 + 有界缓存 + 双通道降级，设计合理。

## 5. 内存占用审查（新增）

### 5.1 项目自建基线（`docs/memory-optimization-plan.md` §8，debug 口径真机采样，2026-09-12）

| 口径 | 数值 |
|---|---|
| 稳态 Private Commit | ~104 MB（含 GPU 栈、字体 ~22MB） |
| 隐藏态 Working Set（修剪后） | 14–20 MB |
| 可见态 Working Set | ~30 MB |
| 10.4 小时长跑 | 零增长 |
| 热键 500 次循环 | +12.2 MB（门限 +50MB/+30%，达标） |

### 5.2 主动内存管理措施（均已核实落地）

1. **隐藏后工作集修剪**（M1，`EmptyWorkingSet` 类调用）：隐藏态 WS 压到 14–20MB。
2. **字体栈 mmap 化**（M2，唯一动私有提交的措施）：20+MB 字体不再整块进私有提交。
3. **图标纹理缓存隐藏即清空**（M3）：唤起重解码——用 CPU 换内存的明确取舍。
4. **明确不做清单**（§5）：nucleo Matcher 复用（测量驱动判定不做）、swap 链压缩等，防过度优化，有测量口径支撑。
5. 协议帧 1MiB 上限、stderr 捕获 64KB 上限、图标读盘 512KB/尺寸 512 上限（S-04，`ImageReader` + `max_alloc` 16MiB）、PATH_INDEX 512 上限、剪贴板文本 1MiB 上限（S-07）——**各类无界输入均有界**，这点做得比多数桌面软件完整。

### 5.3 残留风险

1. **FrozenCache 落盘桩无完整性校验**（可写缓存目录者可伪造显示层内容；点击后仍路由真实扩展，影响限于显示欺骗）。
2. **framing 解码缓冲**单条上限 1MiB 但 buffer 本体在毒化前随输入增长（已由 S-02 修复为有界），无残留。
3. 104MB 稳态 PRIV 对 egui 应用属于正常偏上（GPU 驱动栈占大头），隐藏态修剪后 14–20MB 常驻非常克制。

## 6. 安全与正确性结论（承第一轮，复核后定稿）

- **现存高危：无。** S-01（`cmd /C start` 引号错配注入）修复彻底（换汇点 + `include_str` 回归护栏），S-03 open_url scheme 白名单、S-05 信任台账、S-07/S-08 门控均已在源码核实。
- **应修中低危**：
  1. P1 shell 管道死锁（正确性，用户可感知）；
  2. P2 calc 大数饱和显示（正确性，计算器最坏缺陷类型）；
  3. P3 framing O(n²)（半可信输入 DoS 面）；
  4. UI-6/P4 Shell 确认门误导呈现（社会工程面）。
- **已声明取舍（记录在案）**：trust.json 无签名（非防篡改）、hash-then-spawn TOCTOU、file:// 任意本地打开、emoji 移除、非 Windows AutoTrusted。
- **卫生项**：MSRV 未声明（`manifest.rs:303` 接受 `.cmd`/`.bat`，建议 `rust-version ≥ 1.77.2` + 拒绝 .bat/.cmd）；`reveal_in_folder`（dd-gui 侧）无 S-08 同款字符门控；`path_to_file_url` 不做百分号编码（§9.6 自记档未修）。

## 8. 结语

dd-run 是一个**工程纪律显著高于平均水平**的项目：契约注释-设计稿-测试三层对齐、安全自审计真实闭环、内存有基线台账且含"明确不做"清单、UI 对 IME/多屏/钩子不可靠性等 Windows 真机痛点有针对性处理。现存问题集中在**执行面正确性**（P1/P2）、**半可信输入的复杂度边界**（P3）与 **UI 便利性缺口**（长列表导航、确认门文案），均为小到中工作量可收口的局部问题，不构成架构性返工理由。
