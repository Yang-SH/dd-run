## 3. 测量方法与口径

- **驱动方式**：按协议（JSON-RPC 2.0 over NDJSON，§2.2）直接向 sidecar 进程发 `initialize` → `get_items(page_id="files.results", search_text=…)`，**不经 GUI**，避免宿主调度与渲染开销混入计时。
- **计时口径**：写入请求行 → 读到**匹配 id** 的响应行，含 stdin/stdout 管道往返。
  **该值 ≥ 扩展进程内耗时**，故「本值达标」可**推出**进程内达标（用上界达标证明内层达标）；反之不达标时需进一步分解。
- **耗时分解**：空查询仍会执行可用性探活但直接返回提示项 → 该值为「探活 + 协议往返」地板；无命中查询走完整 IPC 但结果集为空 → 该值为「IPC 往返」地板；命中查询 = IPC + skim 评分 + 排序。
- **资源采样**：`psutil` 采子进程 RSS / 线程数 / 句柄数；**基线取预热后稳态**（预热 10 次），避免把首次分配计成「增长」。
- **通道切换证据**：stderr 由独立线程按**到达时刻**打戳收集（`DDRUN_LOG=debug`）。
- **故障注入**：终止 Everything **桌面实例**（保留服务实例）以造「IPC 不可用」；重启后按**时间**轮询恢复（不能用「N 次查询」——引导项响应仅 0.1 ms，N 次会瞬间跑完，等于没等）。

复现命令：

```bash
cargo +stable-x86_64-pc-windows-gnu build --release -p dd-ext
# 解释器需含 psutil（否则资源序列与进程枚举静默为空）
PY="/c/Users/y7398/.workbuddy/binaries/python/envs/default/Scripts/python.exe"
export DDRUN_ES_PATH='C:\Users\y7398\AppData\Local\Microsoft\WindowsApps\es.exe'   # 或装到 PATH / Everything 目录
"$PY" tools/search_acceptance.py env
"$PY" tools/search_acceptance.py breakdown -n 100
"$PY" tools/search_acceptance.py bench -n 1000 --warmup 10 --sample-every 50
"$PY" tools/search_acceptance.py fault -n 20 --settle 8 --recover-timeout 120 --poll-interval 2
```

### 3.1 测量闸门（2026-09-17 新增，防「假达标」）

本轮实测踩到两个**会让结论完全失真**的坑，故这三道闸门已写进脚本（不再是靠人记得）：

| 闸门 | 判据 | 防的是什么 |
| --- | --- | --- |
| **IPC 就绪闸门**（`wait_ipc_ready`） | 计时前轮询到 `channel=ipc` 才放行；未就绪直接 `SystemExit`（不做测量） | Everything 刚启动、DB 未加载完时 `everything_available()=false` → `get_items` **直接返回引导项（~0.14 ms）**。照常计时会得出「p50 0.14 ms 达标」的**虚假结论**（本轮实测：1000 次查询总耗时不足 0.2 s，正是「全是引导项」的特征） |
| **通道直方图** | 只统计**计时循环内**的查询；`a33_05_all_queries_over_ipc` 为两个 IPC 门禁与基线降幅的**前提** | 引导项 / 回落通道混入计时；就绪探测与预热阶段的引导项污染统计 |
| **通道级恢复判据** | A-33-10 的「恢复」= 通道回到 `ipc` | es 回落会在 ~0.2 s 内回响应，按「有响应即恢复」判会把它误判成 IPC 已恢复（首轮脚本实现在 0.25 s 就报「恢复」） |

**基线采法**：`run_es` 与扩展内部**完全同参**（`es.exe -json -n 30 -size -dm -attributes <q>`，`RESULT_LIMIT=30`），轮转同一组 16 类查询 ×200 次取 p95；口径是**完整进程往返**（spawn + 查询 + 解析），即「不经 dd-run 直接用 Everything 命令行」的等价路径 —— 量化的是**通道收益**。

### 4.2 A-33-06（IPC 不可用 100 % 回落 `es.exe`；两者均不可用 100 % 引导项；单请求 ≤ 2000 ms）

**结论（2026-09-17，两分支均实测）**：判据里的两种「IPC 不可用」形态**都真实存在、且都已被测到**，故不再是「部分通过」：

| 形态 | 触发条件 | 期望 | 实测（v1.3） |
| --- | --- | --- | --- |
| ① **两者均不可用** | IPC 探活 false（实例不在/不可达）**且** `es.exe` 探活也 false | 100 % 引导项 | **20/20 引导项**（`files.guide`，通道 `none`），p50 0.143 ms、p95 0.20 ms、max 760 ms ≤ 2000 ms ✅ |
| ② **IPC 不可用但 es 可用** | IPC 探活 true（Everything 窗口已回来）但**缓存的 client 仍持旧窗口句柄** → 查询失败 | 100 % 回落 `es.exe` 且返回结果 | **3/3 回落**（通道 `ipc->es`），**每次返回 30 条真实结果**，total 224.98 / 246.88 / 282.47 ms，其中 `query`（es 进程往返）224.78 / 246.58 / 254.47 ms ✅ |

**为什么有两种形态**：`everything_available()` = **IPC 探活 OR es 探活**（`search.rs`）。桌面实例被终止后：IPC 探活 false，`es.exe -get-everything-version` 也 false（同一会话内无实例可答）→ 形态①。实例重启后窗口很快回来 → 探活 true，但扩展缓存的 client 仍指向旧窗口 → 形态②（这正是 A-33-10「只降级不恢复视为不合格」要覆盖的窗口期）。

**首轮为何只见引导项**：2026-09-15 本机无 `es.exe`，形态① 是唯一可达状态（形态② 的回落必然失败），故当时只测到引导项、回落半标 🟨。

#### 4.2.1 本轮发现的缺陷：回落失败被静默当成「无结果」（已修，v1.3 产物）

- **现象（修复前）**：形态② 下若 `es.exe` 自身也失败，用户看到的是**空结果列表且无任何提示**；`get_items` 返回 0 项、无错误、无引导。
- **根因**：`run_es`（`search.rs`）把 `es.exe` 的 **stderr 丢弃**（`Stdio::null()`）且**忽略退出码**（`let _ = child.wait();`），而 `parse_response("")` 被刻意设计为「空输出 = 无匹配结果」。二者叠加后，「es 失败」与「真的没搜到」**无法区分**。实测形态：`es.exe` 以 **`rc=8`** 退出，错误只写在 stderr —— `Error 8: Everything IPC not found. Please make sure Everything is running.`
- **修复**：把「输出 + 退出码 + stderr」三者的判定收口为纯函数 `interpret_es_output(status, stdout, stderr)`：仅 `rc=0` 才按「无结果」处理（保持既有语义），`rc≠0` 一律转 `Err` 并**保留 es 的 stderr 文案** → 上层落成可读的 `files.error` 项（文案指向安装/运行 Everything 与 `DDRUN_ES_PATH`）。同时 `run_es` 改为 **stdout/stderr 双管道并发消费**（避免写满管道阻塞）并带出退出码。
- **验证**：新增单测 `interpret_es_output_separates_no_result_from_failure`（5 个断言面：rc=0 空输出仍为无结果 / rc=0 合法 JSON / **rc=8 + 空 stdout 必须 Err 且带 stderr 文案与退出码** / 无退出码 / rc=0 但非法 JSON 仍报错）；`cargo test --workspace` **433 passed / 0 failed**。
- **副产证据（形态②下的 es 成功率）**：本轮形态② 的 3 次回落**全部成功**（Everything 窗口已在、`es.exe` 可答），故修复后的「es 也失败 → 可读错误项」路径**未在本轮真机复现**，仅由单测锁定其行为（诚实记录）。

- 副带证据：`es.exe` 缺失路径返回的是**可读错误项**（`files.error` 文案指向「请安装并运行 Everything，并确保 es.exe 可用（或设 DDRUN_ES_PATH / DDRUN_EVERYTHING_DIR）」），即「两者均不可用」时**不是静默失败**。

### 4.5 A-33-10（Everything 退出→重启后 N 次查询内自动回 IPC；不得永久停留回落态）

表：三轮故障注入的恢复过程（**恢复判据**：v1.3 起为「通道回到 `ipc`」，前两轮是「有响应」）。

| 轮次 | 日期 | 轮询间隔 | 「不可用」阶段 | 恢复点（通道 `ipc`） | 恢复耗时 |
| --- | --- | --- | --- | --- | --- |
| 1 | 09-15 | 2.0 s | 引导项 0–10 s（DB 未加载）→ `error` ×3（t=12/14/16 s） | **第 10 次查询** | **18.06 s** |
| 2 | 09-15 | 0.5 s | 引导项 0–10.5 s | **第 22 次查询** | **10.55 s** |
| **3** | **09-17** | 2.0 s | 引导项 ×4（0–8.6 s）→ **`ipc->es` 回落 ×3**（8.6–13.1 s） | **第 8 次查询** | **15.16 s** |

**轮次 3 的逐次轨迹（含通道，v1.3）**：

```
n=1  t= 0.02s  guide   channel=none     0.226 ms   ← IPC 探活 false + es 探活 false（两者均不可用）
n=2  t= 2.04s  guide   channel=none     0.232 ms
n=3  t= 4.26s  guide   channel=none   200.561 ms   ← 探活带 3 s TTL，此处发起了真实探测
n=4  t= 6.29s  guide   channel=none     0.246 ms
n=5  t= 8.59s  results channel=ipc->es 283.279 ms   ← 探活转 true，但 client 持旧窗口句柄 → 回落 es（成功）
n=6  t=10.84s  results channel=ipc->es 225.783 ms
n=7  t=13.11s  results channel=ipc->es 247.682 ms
n=8  t=15.16s  results channel=ipc      27.849 ms  ← 达 REBUILD_AFTER_FAILS=3 → 释放 client → 重建 → 回 IPC
```

**轮次 1 的定因链（通道切换日志，按到达时刻）**：

```
t= 32.739s  [dd-ext-filesearch] IPC 查询失败（query timed out），回落 es.exe
t= 34.740s  [dd-ext-filesearch] IPC 查询失败（query timed out），回落 es.exe
t= 36.743s  [dd-ext-filesearch] IPC 连续 3 次失败，已释放 client，下次重建
t= 36.743s  [dd-ext-filesearch] IPC 查询失败（query timed out），回落 es.exe
```

即：**探活先在 Everything 重启早期为 false（DB 未加载）→ 引导项**；DB 加载后探活转 true，但**缓存的 client 仍持有旧实例的窗口句柄** → 查询失败并按 `REBUILD_AFTER_FAILS = 3` 的阈值释放 client → 下一次查询经 `shared()` 重建 → 恢复 IPC。**这正验证了「只降级不恢复视为不合格」的设计要求**。

轮次 2 未见回落阶段（在 22 次查询内直接回到结果），说明恢复路径**不唯一**（与窗口句柄是否被复用有关）——三轮都能在**约 10–18 s / 10–22 次查询**内回到 IPC，**长驻进程不会永久停留回落态** ✅。

> ⚠️ **判据修正留痕**：前两轮的「恢复」是**按「有响应」**判定的。本轮实测证明该判据**不可靠** —— 有 `es.exe` 时回落通道会在 ~0.2 s 内回响应，会把「回落可用」误判成「IPC 已恢复」（本轮若沿用旧判据将在第 5 次 / 8.59 s 就误报恢复，实际 IPC 直到 15.16 s 才回来）。故脚本改为 `channel == "ipc"` 判据（§3.1）。

## 6. 副产物发现

- **O1 封套校验在真实子进程上生效（旁证）**：首版测量脚本误把信封的 `jsonrpc` 写成 `"1.0"`（应为 `"2.0"`；`1.0` 属 `initialize.params.protocol_version`），sidecar **立即**返回 `-32600` 且 `data.reason = unsupported_jsonrpc_version` —— 未崩溃、未静默，属 O1 落地的端到端旁证。
- **`es.exe` 以 `rc=8` 失败时错误只在 stderr（产品缺陷的触发条件，2026-09-17）**：`es.exe -json …` 在「同一会话内无可用 Everything 实例」时 stdout 为空、**stderr 写 `Error 8: Everything IPC not found.`**、退出码 8（实测 219–835 ms 后返回）。旧 `run_es` 丢弃 stderr + 忽略退出码 → 静默降级为空结果；修复与验证见 §4.2.1。
- **`es.exe` 与扩展的会话边界**：服务实例（会话 0）**不能**为会话 1 里的 `es.exe` 提供 IPC（`-get-everything-version` 同样回 rc=8）—— 故「桌面实例被杀、服务实例仍在」这一状态对用户而言等同「Everything 不可用」，走引导项（§4.2 形态①）。
- **测量假达标（方法论）**：Everything 刚启动/DB 未加载时，`get_items` 返回引导项仅需 **0.14 ms**，若不加闸门会得出「p50 0.14 ms 远超预期」的**完全虚假结论**（本轮实测踩到，脚本已加 §3.1 的三道闸门）。**结论：低延迟类验收必须校验「测的是哪条通道」，而不只是看数字好看。**
