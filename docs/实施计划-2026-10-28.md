## 1. 结论

本文把路线图 §3 六条工作流落成**四个波次 + 一条需求驱动通道**的执行序列；每一步给出做法、命令与量化验收，技术口径一律引用权威文档、不另立标准。本文撰写前已完成一轮全量核对与基线实测（§8），其中 cargo-deny 允许清单已本机实证（§2.3）。

**推荐实施顺序**：

| 波次 | 内容 | 工作流 | 前置条件 | 预估 |
|---|---|---|---|---|
| ① | 质量与安全收口：文档回写 → 虚拟化判定 bench → cargo-deny 门禁 → fuzz 初始化起跑 | S1 | 无（纯本地） | 1–2 天 |
| ② | 结构与文档纪律：refactor 批次 B→C→D→E（S3 代码腿可并行）→ docscan 二阶段 → conformance 实跑腿 | S2（+S3 代码腿） | 波次①起跑即可并行（仅 fuzz 夜跑验收时钟挂起等待） | 1–2 周 |
| ③ | 发版收口：CHANGELOG 归段 → snapshot/bench 转阻塞 → tag → SHA256SUMS/provenance 端到端验证 | S4 | 波次①②闭环 | 1 天 |
| ④ | 真机清账：按硬件条件聚合会话逐腿销项 | S5（+S3 真机腿） | 外部机器 / 用户会话窗口 | 随外部条件 |
| — | 功能候选池与 recency 观测 | S6 | 需求出现 | 不排期 |

**调度理由（与路线图 §5 节奏表的差异说明）**：

1. **fuzz 验收时钟最早启动**：S1 验收要求「连续 7 天夜间零 crash」——初始化每晚一天，S2 的整体收口就晚一天。fuzz 初始化放波次①最后一步，其 7 夜观察窗口与波次②的 refactor 期间自然重叠，零额外等待。
2. **S3 的代码腿（内置扩展 TODO ×4）从「随外部条件」提前到波次②并行**：四处实现面全在 `crates/dd-ext/src/builtins/`，与波次②的 dd-gui refactor（批次 B–E 只动 dd-gui）**零文件交集**；且非 Windows 分支由 linux / macOS CI 门禁直接验证，不需要真机。真机腿（O6 ④）仍留波次④。
3. **单一发版承载 S1+S2**（对齐路线图 §1「下一次发版为收口载体」）：S1 的三个新门禁与 S2 的结构重构同批进入发版段，避免两次发版重复履行 snapshot/bench 转正与产物验证。
4. **虚拟化判定 bench 先于 refactor**：判定对象 `ui/panel.rs` 不在批次 B–E 搬运范围内，判定结论不受纯搬运影响；先跑先定案。

**不可并行的硬约束**（引 [refactor-structure](./refactor-structure-2026-10-21.md) §4）：批次 E（别名清理）必须最后做——A–D 会新增 `dd_gui::` 自引用行；逐批独立提交、逐批验收、逐批可回滚。

### 2.4 步骤 4——协议 fuzz 初始化（清单 §2.2，七夜验收时钟自此起跑）✅ 已完成（2026-10-30，时钟待 push 后起跑）

- 目录结构（cargo-fuzz 惯例，独立 crate、独立 lock，**主 Cargo.lock 零新增**；根 workspace members = `crates/*` 无需改动——fuzz/Cargo.toml 须自带隔离 `[workspace]` 表，cargo fuzz init 模板默认含 `[workspace] members = ["."]`，若生成的模板缺失则手动补上）：

  ```text
  fuzz/
  ├ Cargo.toml            # [dependencies] dd-protocol = { path = "../crates/dd-protocol" } + libfuzzer-sys
  ├ fuzz_targets/
  │ ├ decoder.rs          # target 1
  │ └ envelope.rs         # target 2
  └ corpus/
    ├ decoder/            # 种子：合法 NDJSON 帧、超长行、截断 UTF-8、bare \n 等
    └ envelope/
  ```

- 两个 target 的判据（清单 §2.2 原文口径，API 已核对）：
  - `decoder`：任意 bytes → `Decoder::with_default_limit()` 后 `push(data)` 返回 `Vec<Frame>`（该 API 无 Err 分支）——断言**永不 panic**；
  - `envelope`：任意 bytes → `std::str::from_utf8` 后 `dd_protocol::validate(line)`（返回 `Envelope`，含 InvalidReason 分支）——断言**永不 panic**。
- 本地验证尝试（可选）：`cargo install cargo-fuzz --locked` + `rustup toolchain install nightly`，再 `cargo fuzz run decoder -- -max_total_time=600`。若本机工具链不可行（与 cargo-deny 同类风险），**直接走 CI 观察模式**，不阻塞初始化。
- CI 夜间 job（**独立 workflow 文件 `fuzz.yml` 放 `.github/workflows/` 目录、仅 `on: schedule` 触发**——勿向 ci.yml 加 schedule：其 `on:` 现仅 push / PR（2026-10-29 实测），加了 schedule 会让 build / test / 三平台 / snapshot / bench 全套门禁每晚全量重跑）：

  ```yaml
  fuzz:
    name: protocol fuzz (nightly, observation)
    runs-on: ubuntu-latest
    if: github.event_name == 'schedule'
    continue-on-error: true        # 观察模式：七夜零 crash 后随 S4 转阻塞
    steps:
      - uses: actions/checkout@<同仓既有 pin>
      - run: rustup toolchain install nightly --profile minimal
      - uses: taiki-e/install-action@<同仓既有 pin>
        with:
          tool: cargo-fuzz
      - run: cargo fuzz run decoder -- -max_total_time=600
      - run: cargo fuzz run envelope -- -max_total_time=600
      - if: failure()
        uses: actions/upload-artifact@<同仓既有 pin>
        with: { name: fuzz-crash, path: fuzz/artifacts }
    # schedule: cron 建议每晚一次（如 '0 21 * * *' UTC），维护者可调
  ```

- 量化验收（清单 §2.2 原文）：**连续 7 夜** schedule job 零 crash；`Decoder` 在 ≥ **10⁷** 次执行后无 panic（OOM 与 `TooLarge` 路径除外——即 `-rss_limit_mb` 触发的 OOM 与单帧超限路径不计）；语料种子入库。满足后：清单 §2.2 销项 + fuzz job 随 S4 转阻塞。
- 回写：implementation.md 台账行记七夜观察结果；CHANGELOG 新条目。
